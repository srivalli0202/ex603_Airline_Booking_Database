# Unit 1 Analysis

## Modelling Justification
The Airline Booking Database is designed to organize information about passengers, flights, bookings, airports, and flight routes. I selected these five entities because each one represents an important part of the airline booking process. The passenger's relation stores information about travelers, while the flights relation stores details about available flights. The bookings relation connects passengers to the flights they reserve.  The airports relation stores airport information, and flight_routes connects flights with airports. Keeping this information in separate relations reduces repeated data and makes the database easier to organize, update, and maintain.

## Primary Key
Primary key is unique for each main relation so that every record can be identified correctly. The passenger_id uniquely identifies each passenger, flight_id identifies each fllight, booking_id, identifies each booking, airport_id identifies each airport. Using ID values as primary keys makes it easier to connect related information without depending on names or other values thar could change. For the flight_routes relation, I used a composite primary key made up of flight_id and airport_id. This combination prevents the same flight and airport relationship from being entered more than once.

## Relationship's between the tables
The relationships between the relations represent how the different parts of the airline booking system work together. A passenger can make multiple bookings, while each booking belongs to one passenger. A flight can also have multiple bookings, while each booking is associated with one flight. The flight_routes relation connects flights and airports using flight_id and airport_id as foreign keys. This allows a flight to be associated with airports without repeating the complete flight or airport information. These relationships make it easier to retrieve connected information, such as finding all bookings made by a passenger or identifying the airports associated with a flight.

## ON DELETE decisions
ON DELETE behaviors to protect related data in the database. For the foreign keys in bookings, I used ON DELETE RESTRICT for both passengers and flights. This prevents a passenger or flight from being deleted while booking records still reference them, which helps preserve important booking information. I also used ON DELETE RESTRICT for airports because an airport should not be deleted while it is still referenced by a flight route. However, I used ON DELETE CASCADE for flight_routes.flight_id. If a flight is deleted, its related route records are automatically deleted because those route records are no longer needed without the flight.

## Rules enforced by the database
I also chose to enforce important data rules directly in the database schema. For example, passenger_name, airport_name, and flight_number should not be NULL because these values are required for the system to work correctly. The fare and fare_paidvalues shoukd be greater than or equal to zero so that negative prices cannot be stored. The database should also ensure that arrival_time is later than depature_time. Enforcing these rules in the schema helps maintain accurate and consistent data even if information is entered from different applications or tools. This provides strong er protection than relying only on application level validation.

### Reflection
One design that another designer could reasonably make differently is the primary key for the flight_routes relation. In my design, I used to comnination of flight_id and airport_id as a composite primary key. Another designer might choose to create a seperate flight_rouite_id as the primary key instead.I chose the composite key because the combination of a flight and an airport already identifies the relationship between them. It also prevents the same flight and airport combination from being stored more than once. This keeps the relation simple and avoids adding an extra identifier that is not currently necessary.
This design also fits the expected read and write patterns of the airline booking platform. The system will frequently read route information when users search for flights and airports, while route records will be added or changed less frequently. Using flight_id and airport_id directly makes it easy to find the airports associated with a flight without depending on a additional route identifier. however, if the system becomes more complex in the future and needs to store additional route information, such as the order of stops, a separate flight_route_id could be useful. For the current requirements, I believe the composite primary key provides a simple and appropriate design.
